\section{Introduction to Algorithms}

\subsection*{Problems and Instances}

Algorithms are for solving problems.
See Figure~\ref{fig:problem-algorithm}.
In (theoretical) computer science, a \emph{problem} must be
defined formally, usually by specifying the input and the required
output.

For example, consider the \emph{sorting problem}. The input is an array
$A=[a_1,a_2,\ldots,a_n]$, and the output is an array containing the same
elements in nondecreasing order.

A problem is a general specification; a particular input to the problem is
called an \emph{instance}. For example, one instance of the sorting problem is
$A=[4,2,10,-5,8]$, and its corresponding output is
$[-5,2,4,8,10]$. The
relationship between a problem and an instance is similar to that between a
\emph{class} and an \emph{object} in an object-oriented programming language.
Equivalently, we may think of a problem as the collection of all its possible
instances together with the required output for each one.

\begin{figure}[h]
\centering{\input{problem-algorithm}}
\caption{The relationship among a problem instance, an algorithm, and its output.}
\label{fig:problem-algorithm}
\end{figure}


As another example, consider the \emph{selection problem}. Its input consists
of an array $A=[a_1,a_2,\ldots,a_n]$ and an integer $k$ satisfying
$1\le k\le n$; its output is the $k$-th smallest element of $A$. For the
instance $A=[4,2,10,-5,8]$ and $k=2$, the output is 2.

\subsection*{Principles of Algorithm Design}

An algorithm is a finite sequence of unambiguous instructions for solving a
problem; it takes an instance of the problem and produces the correct output.
These instructions may be carried out by a person or implemented
as a computer program. For many problems, a straightforward approach is to
enumerate all candidate solutions and return the correct one~(e.g., satisfying the required
specifications). This approach is called \emph{brute force}. Although it may work
for small instances, it is generally \emph{inefficient} because the number of
candidates can be prohibitively large.

We focus on the design of \emph{efficient} algorithms. Here,
``efficient'' means ``runs in polynomial time,'' a notion that we will elaborate
in \Cref{part:computational-complexity}.
Two principles underlie the design of efficient algorithms in this book.

\begin{enumerate}

  \item \emph{Partition the problem into smaller subproblems.} This principle
  focuses on the structure of the problem. One strategy reduces a problem of
  size $n$ by a constant size, such as transforming it to subproblems of
  size $n-1$. This strategy leads to dynamic programming
  algorithms~(Part~\ref{part:dynamic-programming}). Another strategy divides a
  problem of size $n$ into subproblems whose size is a
  fraction of the original size, such as $n/2$. This strategy leads to
  divide-and-conquer algorithms~(Part~\ref{part:divide-and-conquer}).

  \item \emph{Improve the solution iteratively.} This principle focuses on the
  solution itself. We begin with an initial solution and gradually refine it
  until we obtain a correct or optimal solution. One strategy starts with a
  feasible but nonoptimal solution and repeatedly improves it; network-flow
  algorithms~(Part~\ref{part:network-flow}) follow this idea. Another strategy
  starts with a partial solution and extends it step by step until it becomes a
  complete solution; greedy algorithms~(Part~\ref{part:greedy-algorithms}) follow
  this approach.

\end{enumerate}

\subsection*{Relationships among Problems}

In addition to designing algorithms for individual problems~(the first goal
of this book) we study the relationships among problems. Understanding these
relationships is the second goal of this book and is important for the following
two major reasons.
\begin{enumerate}
\item They allow us to solve new problems using existing algorithms. For
example, suppose that we can transform problem $X$ into problem $Y$~(\Cref{chap:reduction})
and we already know an efficient algorithm for $Y$, then we can use that problem
to solve $X$ efficiently. 
Such transformations are powerful as they enable a relatively small
collection of algorithms to solve a much broader range of problems. Examples
include \Cref{chap:half-plane-intersection,chap:2sat,chap:tramp-steamer,chap:max-matching,chap:project-selection,chap:baseball-elimination}.
\item They allow us to show that a problem is hard. Suppose 
problem $X$ can be transformed into problem $Y$, and we already know that
there does not exist
efficient algorithm for $X$, then we can conclude that problem $Y$ 
cannot be solved efficiently either~(because, otherwise, 
that algorithm for $Y$ would then yield an efficient algorithm for $X$).
Establishing such relationship therefore help us
avoid an unproductive search for an efficient algorithm as such algorithms
may not exist. We develop techniques for proving hardness in
\Cref{chap:reduction,chap:npcomplete}.
%\item They allow us to organize problems into classes and understand the
%relationships among those classes. This classification is a central goal of
%the \emph{theory of computational complexity}, which we study in
%Part~\ref{part:computational-complexity}.
\end{enumerate}

\subsection*{Example of Algorithm Design and Analysis}

Consider the problem of \emph{merging two sorted arrays}. The input consists
of arrays $A[1\cdots m]$ and $B[1\cdots n]$, each sorted in nondecreasing
order, and the output is a sorted array $C$ containing all $m+n$ elements of
$A$ and $B$, including duplicates. For example, if
$A=[-4,2,5,8]$ and $B=[-3,2,3,4]$, then the output is
$C=[-4,-3,2,2,3,4,5,8]$.

Let us design an algorithm for this problem. You may wish to pause first and
think about how to construct one. The algorithm builds $C$ incrementally and
can therefore be viewed as a greedy algorithm. At each step, it appends the
smallest element of $A$ or $B$ that has not yet been copied to $C$. To identify
this element efficiently, we maintain two pointers/indices, $k_A$ and $k_B$. Each index
points to the first unprocessed element of its corresponding array. We compare
$A[k_A]$ with $B[k_B]$, append the smaller element to $C$, and advance the
corresponding index. The pseudocode appears below.

\begin{algorithmblock}[0.8\textwidth] \label{code:merge-two-sorted-arrays}
	\aaA {12.8}{function merge-two-sorted-arrays ($A[1\cdots m], B[1\cdots n]$)}\xxx
	\aab {initialize an empty array $C$;}\xxx
	\aab {initialize indices $k_A = 1$ and $k_B = 1$;}\xxx
	\aab {choose a sentinel $M$ larger than every element of $A$ and $B$;
		set $A[m + 1] = M$ and $B[n + 1] = M$; (think: why is this useful and necessary?)}\xxx
	\aaB {7}{for $k = 1 \to m + n$ }\xxx
	\faC {3}{if $A[k_A] \le B[k_B]$ }\xxx
	\aad {$C[k] = A[k_A]$; }\xxx
	\aad {$k_A = k_A + 1$; }\xxx
	\aaC {3}{else}\xxx
	\aad {$C[k] = B[k_B]$; }\xxx
	\aad {$k_B = k_B + 1$; }\xxx
	\aab {return $C$;}\xxx
\end{algorithmblock}


An analysis of an algorithm has two main components: proving its correctness
and determining its running time.

We first prove correctness: the resulting array $C$ is in nondecreasing order
and contains every element of $A$ and $B$ with the correct multiplicity.
Although this claim may seem evident, it requires a formal argument. We prove the
following \emph{invariant}. An invariant is a statement about the algorithm's data structures
that remains true throughout the algorithm. Here, the data structures consists of $C$ and the indices
$k_A$ and $k_B$.

\emph{Invariant:} For each $k=0,1,2,\ldots,m+n$, after the $k$-th iteration of the for-loop,
$C[1\cdots k]$ contains the $k$ smallest elements in $A$ and $B$, in nondecreasing order, 
and $k_A$ and $k_B$ index the first elements of $A$ and $B$, respectively, that have not yet been
copied to $C$. 
%if an array has been exhausted, its index points to the sentinel $M$.

\begin{proof}
We prove the invariant by \emph{induction} on $k$. For the base case $k=0$,
$C$ is empty, and $k_A=k_B=1$. Thus, each index points to the first, and hence
smallest, unprocessed element of its sorted array. The invariant therefore
holds before the first iteration.

For the inductive step, assume that the invariant holds after iteration $k$,
i.e., $C[1\cdots k]$ contains the $k$ smallest input elements
in nondecreasing order, and the values $A[k_A]$ and $B[k_B]$ are the smallest
unprocessed elements of their respective arrays. 
Their minimum is therefore the smallest unprocessed input
element overall. During iteration $k+1$, the algorithm appends this value to
$C$ and advances the corresponding index. Consequently, $C[1\cdots k+1]$
contains the $k+1$ smallest input elements in nondecreasing order, and both
indices again identify the first unprocessed elements of their arrays. 
Hence, the invariant holds after iteration $k+1$.
\end{proof}

After iteration $m+n$, the invariant states that $C$ contains all $m+n$ input
elements in nondecreasing order. Thus, the algorithm returns the correct
merged array.

We next analyze the algorithm's running time. We measure the running time
by counting its \emph{basic operational units}. The precise cost of an operation depends on the computational
model and hardware. In practice, we treat a variable assignment, 
an elementary arithmetic operation, an array access, or a comparison as taking one unit.
%The worst case is w.r.t.\ all instances, i.e., the instance takes largest number of computing units.

%Let $T(m,n)$ be the running time of this algorithm when $|A| = m$ and $|B| = n$.

Let's count the number of basic operations required by above algorithm.
Let $|A|=m$ and $|B|=n$. Line 2 takes one unit to initialize $C$; line 3
takes two units to initialize the two indices; and line 4 takes two units to
store the sentinels. The loop performs $m+n$ iterations, so the loop-index
advance on line 5 contributes $m+n$ units, and the comparison on line 6
contributes another $m+n$ units. During each iteration, exactly one branch is
executed: either lines 7--8 or lines 10--11. Each branch copies one element to
$C$ and increments one index, for a total of $2(m+n)$ units over all
iterations. Finally, line 12 takes one unit to return $C$. 
We use $T(m,n)$ to denote the total number of units; we have
\[
T(m,n)=1+2+2+(m+n)+(m+n)+2(m+n)+1=4m+4n+6.
\]

It is important to distinguish the \emph{input} from the \emph{input size},
and to emphasize that the running time of an algorithm is a function of the input size.
Here, the actual input consists of two arrays, $A$ and $B$, whereas the
input size is their total lengths $m+n$. 
%The running time of the above algorithm depends only
%on the input size; in other words, the actual numbers stored in $A$ and $B$
%do not affect the running time.
More precisely, the input size is defined as the amount of memory needed to
store the actual input. In most practical settings,
each number fits in a fixed-size word, such as 32 bits.
Under this assumption, the amount of memory needed to store $A$ and
$B$ is $32\cdot (m+n)$ bits. The running time $T(m, n)$ can be written
as $(32\cdot(m+n)) / 8 + 6$, in terms of the input size.
Clearly, this running time grows linearly with the input size.

The exact coefficients and constant term in $T(m,n)=4m+4n+6$ depend on which
operations the model counts and how their costs are assigned. For algorithm
analysis, we are usually more interested in how the running time grows as the
input size grows. We therefore write $T(m,n)=\Theta(m+n)$, meaning that the
running time grows asymptotically at the same rate as function $m+n$. The next chapter
introduces the notation used to describe such growth rates for algorithm analysis.
